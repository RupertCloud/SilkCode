How to · Projects

Working on projects

A project is the codebase a Silk Code session acts on — the tree its file tools, git commands, and test runs are confined to. This page covers the whole life of one: creating it, opening it, switching to another, teaching the agent about it, and shipping it.

One session, one project.
Change either one without losing the other.

The model

One session, one workspace

Every session is bound to exactly one workspace root. Tools cannot read or write outside it, run_tests runs inside it, and git status, diffs and pushes all refer to it. Open as many sessions as you like — each can sit on a different project with a different model, and they run side by side.

Local directory

Any folder on your machine. silkcode ~/code/app or the GUI's local tab.

GitHub repository

Picked from the repos your GitHub sign-in can see; cloned for you into ~/.silkcode/projects/.

Brand-new project

silkcode new scaffolds one that already runs and tests, then runs git init and commits it.

Remote-only project

--remote github:owner/repo keeps the checkout in a sandbox; the code never lands on your machine.

Step one, when there is nothing yet

Create a new project

A blank folder is a bad place to start an agent: it has no tests to run, no instructions to read, and nothing to revert to. silkcode new gives you a project that runs and tests on the first try, then makes the initial commit.

# see what's available
silkcode new --list

# create one (git-initialized, with an initial commit)
silkcode new todo-cli --template python-cli

# say what it is — goes into the README, SILKCODE.md and package metadata
silkcode new invoices --describe "Invoice API for freelancers"

# create it somewhere specific
silkcode new site -t web --dir ~/code

# create it and put the agent straight to work
silkcode new invoices -p "add a health endpoint and a test for it"

# create it and stay in the REPL
silkcode new invoices --open

# no arguments: it asks for a name and a template
silkcode new

Names are normalized. "My New App" becomes the directory my-new-app and the package my_new_app. Path separators and reserved directory names are refused rather than guessed at.
Nothing is overwritten. An existing non-empty directory is refused unless you pass --force, and even then files that already exist are kept and reported. Scaffolding inside an existing checkout adds files to that repository instead of burying a nested one, and --no-git skips git entirely. If git is missing, or the machine has no committer identity, you get a printed warning — the project is still on disk.

Step one, when the code already exists

Open an existing project

01

From the terminal

Pass the path. That directory becomes the workspace root for the session.

silkcode ~/code/ridelink              # REPL
silkcode gui ~/code/ridelink          # GUI at 127.0.0.1:8377
silkcode -p "fix the failing test" ~/code/ridelink   # one-shot
02

From GitHub

Sign in once with silkcode connect github. After that, any repository the sign-in can see — private ones included — can be opened by name; Silk Code clones it for you and reuses the clone next time.

silkcode connect github
silk> /project github:acme/widget     # clones into ~/.silkcode/projects/

Clone directories are named <owner>-<repo>-<digest>. The digest is not decoration: - is legal inside both owner and repo names, so facebook/react-native and facebook-react/native would otherwise share a directory — and a push would land in the wrong repository.

03

From the GUI

The ＋ button (new session) asks which project to run the session on: pick a GitHub repository from the list, or type a local path on the second tab. Recently opened projects appear in the same list, so the second visit is one click.

Mid-flight

Switch project without losing the conversation

/project re-points the current session at another codebase. The conversation, checkpoints and token count survive; the system prompt is regenerated so the model orients on the new tree, and files, git and commands all follow.

silk> /project                       # interactive picker
silk> /project ~/code/other-app      # straight to a local path
silk> /project github:acme/widget    # clone (or update) and switch
silk> /new scratch-api python         # create one next door and switch to it

/new creates the project beside the current one — /new sibling from ~/code/app creates ~/code/sibling — so scaffolding never drops an unrelated tree inside the repository you are working on.

One writer at a time. Opening the same project in a second session or a second GUI instance is allowed, but the second one is read-only until the first releases the workspace lock (close its session, or take over from the banner).

Make the agent good at your codebase

Teach the project to the agent

Every turn starts with a repo map plus whatever the project tells the agent about itself. Scaffolded projects ship a SILKCODE.md for exactly this reason — an existing project earns the same by adding one.

SILKCODE.md

Project instructions, read on every turn: layout, conventions, the test command, anything the agent should never do. Keep it short and current.

Repo map

Built automatically — the structure and key symbols, so the model knows the shape of the codebase before its first tool call.

Project memory

The agent writes durable notes with the remember tool; read them with /memory. Facts it learned once do not have to be rediscovered.

Skills

Markdown playbooks in the project's skills directory, listed with /skills — repeatable procedures the agent can follow.

# SILKCODE.md — the version a scaffolded project starts with
# Todo Cli

Track todos from the terminal.

## Layout
- `todo_cli/cli.py` — argument parsing and the `main()` entry point
- `todo_cli/core.py` — the logic the CLI calls (keep it importable and testable)
- `tests/` — pytest suite; drive the CLI through `main([...])`

## Conventions
- Keep changes small and focused; explain anything non-obvious in a comment.
- Add or update a test for every behavior change.
- Run `pytest` before committing; the suite must be green.

Prove it, then ship it

Verify and ship a project

The harness runs your suite rather than trusting the model's summary. Test detection is automatic: pytest, npm, cargo, go and flutter are recognized from the project's own files — which is why every scaffold ships a suite the runner can already find.

silkcode testrun the project's tests, framework auto-detected
/diff · GIT DIFFreview exactly what changed before it goes anywhere
/revert · ↩ Revertundo a whole turn from the checkpoint taken before it
/push · ⇧ Pushpush the current branch when you say so
--auto-pushpush unpushed commits after every turn
silkcode reviewan AI review of your uncommitted changes — reads, never writes
silkcode swarmtester + critic + worker iterate until the project scores 10/10

Agent-made commits register Silk Code as co-author, so the record stays honest: git log --grep=X-Silk-Model answers “which commits did the agent write, and with which model?” forever.

When the code should not touch your machine

Sandboxed and remote projects

Two different needs, two different flags. --sandbox keeps the project local but runs the agent's commands in a disposable container. --remote goes further: the repository is cloned inside the sandbox and never lands on your disk at all.

silkcode sandbox serve --token <secret>            # on the machine that should run commands
silkcode sandbox connect http://host:8390 --token <secret>

silkcode --sandbox ~/code/app                      # local files, remote commands
silkcode --remote github:acme/widget               # repo lives only in the sandbox

When it does not go smoothly

Troubleshooting

“already exists and is not empty”
The target directory has files in it. Pick another name, or pass --force to scaffold alongside what is there — existing files are never overwritten either way.
“no initial commit — empty ident name”
Git does not know who you are on this machine. Set it once (git config --global user.email you@example.com) and commit; the project itself was created fine.
The new project has no git repository
Expected when you scaffolded inside an existing checkout: the files belong to that repository rather than a nested one. Use --dir to place it outside, or git init it yourself.
“no test framework detected”
Nothing in the project identifies a runner. Add a suite (or pass --command to silkcode test), and record the command in SILKCODE.md so the agent uses it too.
The session is read-only / a lock banner appeared
Another session or GUI instance holds this project. Close it, or take over from the banner once it is idle.
The GitHub list is empty
Run silkcode connect github (or paste a token in the GUI's GitHub dialog). The picker only lists what your sign-in can actually clone.
