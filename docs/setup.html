How to · Setup

Setting Silk Code up

From nothing installed to typing at your agent from a phone on the train, with the model running on the laptop you left at home. Install takes one command; the rest of this page is about splitting the work across machines.

The phone is a good place to drive a coding agent.
It is a poor place to run the model.

Step one

Install

Python 3.10 or newer, and git. The dedicated installer creates an isolated environment and installs both Silk Code and the Chromium browser used for visual link review. Pick your platform; the differences are real but small.

macOS

macOS ships Python 3.9, which is below the floor. Install a current one first — either from python.org or with Homebrew.

$ brew install python@3.12 git
$ curl -fsSLO https://raw.githubusercontent.com/RupertCloud/SilkCode/main/install.py
$ python3 install.py
$ silkcode version

The first time you run the GUI with --host 0.0.0.0, macOS asks whether Python may accept incoming connections. Say yes, or the phone will simply time out.

Linux

On Debian 12+, Ubuntu 23.04+, Fedora 38+ and their relatives, the system Python is marked externally managed, so a plain pip install stops with error: externally-managed-environment. That is the distribution protecting its own packages, not a Silk Code problem. The dedicated installer creates its own environment and does not modify the system Python.

$ sudo apt install python3-venv git        # or dnf / pacman
$ curl -fsSLO https://raw.githubusercontent.com/RupertCloud/SilkCode/main/install.py
$ python3 install.py
$ silkcode version

A virtual environment works just as well if you prefer one:

$ python3 -m venv ~/.venvs/silkcode
$ ~/.venvs/silkcode/bin/pip install git+https://github.com/RupertCloud/SilkCode

If a firewall is active, the GUI port needs opening before another device can reach it: sudo ufw allow 8377/tcp.

Windows

PowerShell throughout. py is the launcher that comes with the python.org build and is the reliable way to reach the right interpreter.

> winget install Python.Python.3.12 Git.Git
> curl.exe -fsSLO https://raw.githubusercontent.com/RupertCloud/SilkCode/main/install.py
> py install.py
> silkcode version

If that last line reports that silkcode is not recognised, the install succeeded but the Scripts directory is not on your PATH. Either add it, or skip the shim entirely — py -m silkcode.cli.main version runs the same code, and every command on this page works that way.

The firewall prompt is the one to watch. The first time you bind --host 0.0.0.0, Windows Defender asks which networks Python may accept connections on. Tick Private networks. If that dialog is dismissed — and it is easy to dismiss — Windows blocks the port silently, and the symptom on the phone is an indefinite hang rather than any error worth reading.

One syntax difference to know about elsewhere on this page: PowerShell does not accept VAR=value command. Where a POSIX shell takes OLLAMA_HOST=0.0.0.0:11434 ollama serve, set it in your user environment variables instead — which is exactly what silkcode inference host tells you to do when it detects you are on Windows.

Install Tailscale at the same time

Not required, and Silk Code never installs, starts or manages it — but it is the difference between a setup that works on your sofa and one that works on a train, and it is far less annoying to do now than at the moment the LAN address stops answering. Install it on both machines and sign both into the same account:

# macOS
$ brew install --cask tailscale
# Linux
$ curl -fsSL https://tailscale.com/install.sh | sh
# Windows
> winget install tailscale.tailscale
# phone: the App Store / Play Store app, then leave the VPN toggle on

$ tailscale up

Any WireGuard mesh that hands out 100.64.0.0/10 addresses works the same way — Silk Code checks the range, not the vendor. Why this matters, and what the banner looks like afterwards.

Then check what you installed

$ silkcode version
Silk Code 0.2.0+ga07e7a8
  source    commit a07e7a8 on main
  update    silkcode update
  install   /usr/local/lib/python3.12/site-packages/silkcode

That is worth running once now. Because silkcode update pulls whatever is on the branch, the release number alone identifies nothing — everyone tracking main reports the same one while running different code. The +g suffix is what actually names your build, and the update line names the command that updates this particular install, which differs between a git checkout, a pip install from git, and a wheel.

A pip install git+https://… reports that suffix too, which it did not always do: pip records the commit it resolved, and silkcode version reads it when there is no checkout to ask. Without that, the most common install was the one whose bug reports said least.

Updating. silkcode update fast-forwards a checkout, or reinstalls a pip install from the URL and branch pip recorded when you installed it. Every subcommand also answers to its flag form, so silkcode -update and silkcode --update do the same thing. If nothing has changed it says so, rather than announcing an update that did not happen.

The decision

Which machine does what

There are two ways to involve a phone, and they are mirror images. Picking the wrong one is the single most common way to end up fighting this, so it is worth thirty seconds up front.

SetupSilk Code runsThe model runsYou type onGood when
silkcode gui
--host 0.0.0.0		 laptop laptop or cloud phone browser Your code, tools and git are on the laptop. Almost always this one.
silkcode
inference link		 phone (or any second machine) laptop that machine Silk Code is installed where you are typing, and you only want the laptop's GPU.

The first is the one most people want. Your repository, your test runner and your git credentials live on the laptop; the phone is a screen and a keyboard for them. The second exists because a phone or a light laptop can run Silk Code perfectly well and simply has no GPU worth using — so only inference crosses the network.

Setup A

Phone as a screen for the laptop

Run the GUI daemon bound to every interface instead of loopback. That one flag is the whole difference — and it is also why the default is loopback, since binding wider puts a shell-equivalent daemon on whatever network you are attached to.

1

Start the daemon so something else can reach it

Without --host it binds 127.0.0.1, which on a phone means the phone — nothing else on the network can connect, however good the Wi-Fi is.

$ silkcode gui ~/code/my-project --host 0.0.0.0
2

Scan what it prints

Because the daemon is now reachable beyond this machine, it generates an access token by itself — you do not pass --token unless you want to pin a stable one across restarts. The token is 32 characters and no fun to retype on a phone keyboard, so the URL carrying it is also drawn as a QR code.

This daemon is reachable beyond this machine, so it requires an access token.
Open the URL below (it carries the token); share it with nobody you would not
give a shell on this machine.

Silk Code GUI: http://localhost:8377/?token=4Y55WNL_lY9n1lkomrrcnHQD2dJsCk2F

Reachable from another device:
  http://192.168.1.20:8377/?token=…
      LAN - same network only

Point a phone camera at this to open it (LAN):



On the same Wi-Fi only. To reach this from anywhere, put both machines on a
Tailscale tailnet (https://tailscale.com) and use the 100.x address it gives you.
3

Pair the next device without restarting

That banner prints once, at startup. Terminals scroll, and a second device turns up later. The 📱 Pair button in the GUI header asks for the same facts on demand and draws the same QR — so getting a tablet on does not cost you the sessions running in the daemon you would otherwise have to restart.

On a daemon still bound to loopback, that button tells you so and names the flag that changes it, rather than rendering an empty box for you to interpret.

The QR is drawn, not fetched. The GUI is served from your own machine and stays that way — no request leaves it to render the code. Silk Code has one runtime dependency, so the encoder is written against the QR specification directly.

Setup B

Laptop as a GPU for somewhere else

The mirror image: Silk Code runs where you are typing, and only inference crosses the network. Three commands, one on the laptop and two where you are.

1

On the laptop: check it is listening on a reachable address

This is the half that is easy to miss. Ollama, LM Studio, vLLM and llama.cpp all bind 127.0.0.1 by default. That is the right default, and it is the exact reason a phone on the same Wi-Fi gets connection refused — a failure that reads like a network problem and is not one. So the question is not "is it running" but "is it listening somewhere else can reach":

$ silkcode inference host

This machine is reachable at: 192.168.1.20

  http://192.168.1.20:11435       ollama       4 models - reachable from the network
  port 11434 (ollama) is running, but only on 127.0.0.1 - nothing else can reach it
    restart it listening on every interface:  OLLAMA_HOST=0.0.0.0:11434 ollama serve
2

Where you are typing: find it and link it

discover scans the usual ports across the local network; link probes the address before saving it, so a typo fails now rather than on your first prompt.

$ silkcode inference discover
$ silkcode inference link http://192.168.1.20:11435
$ silkcode inference ping --chat   # is it up, and can it actually generate?

Linking never offers an embedding model as the default. An Ollama install usually holds one, it sorts first alphabetically, and handing it to a coding agent fails on the very first turn with an error that explains nothing.

Linking adds a provider; it replaces none. DeepSeek, Kimi, Qwen, GLM, MiniMax, OpenRouter and Cloudflare Workers AI stay exactly one --model away, and --model auto prefers a reachable local server and falls back to whichever cloud provider has a key. A stored token is not treated as proof of reachability — auto will not hand you a laptop that is asleep.

Beyond the house

Reaching it from anywhere

A 192.168.x.y address stops resolving the moment your phone drops to cellular. Putting both machines on a Tailscale tailnet fixes that, and encrypts the traffic on the way — which the plain LAN path does not do.

1

On the laptop

$ brew install --cask tailscale   # or tailscale.com/download
$ tailscale ip -4
100.94.12.7

Sign in when it opens. If you installed the App Store build, the CLI lives inside the app bundle at /Applications/Tailscale.app/Contents/MacOS/Tailscale.

2

On the phone

Install Tailscale, sign in with the same account, and leave the VPN toggle on. That toggle is the whole trick: with it on, the phone reaches 100.94.12.7 over cellular, hotel Wi-Fi, anywhere.

3

Start the daemon exactly as before

Nothing about the command changes. What changes is the banner. Tailscale allocates from 100.64.0.0/10 — the carrier-grade NAT range reserved by RFC 6598 — so an address in that range is a mesh address and nothing else. Silk Code detects it, labels it, sorts it above the LAN address, and puts that one in the QR:

Reachable from another device:
  http://laptop.tail1a2b3.ts.net:8377/?token=…
      Tailscale - works from anywhere on your tailnet
  http://192.168.1.20:8377/?token=…
      LAN - same network only

The URL uses the MagicDNS name rather than the raw 100.x where Tailscale offers one: it survives the node being re-addressed, and it is something you can read off a screen and retype. The address itself is still listed for anyone who wants it.

The "on the same Wi-Fi only" footer disappears, because it is no longer true. Before you get that far, the banner tells you which of these you are actually in — Silk Code reads tailscale status rather than printing the same suggestion regardless:

# not installed
Tailscale is not installed here. Install it on this machine and on the phone…

# installed, never signed in
Tailscale is installed but not signed in. Run:  tailscale up

# installed, signed in, stopped
Tailscale is installed and signed in, but stopped. Run:  tailscale up

Worth knowing

What you are exposing

A Silk Code daemon edits files and runs commands. Anyone who reaches it with the token has, in practical terms, a shell on that machine. The controls are straightforward, but they are worth understanding rather than assuming.

The token is the whole gate

192 bits of randomness, compared in constant time, required on every request — header, cookie or query string. There is no second factor. Treat the pairing URL like an SSH key.

Cross-origin requests are refused

Even with a valid token, a request from another origin gets a 403, and the rebinding guard checks the address that was actually parsed rather than the header as sent.

The token cannot leak by link

The page is served at /?token=… and links out. Every response carries Referrer-Policy: no-referrer, so a click cannot carry the credential to a third party — rather than relying on a browser default to strip it.

Refusals are visible

Environment → Connections shows who connected and who was turned away, and the daemon says something on its own terminal as refusals from a source accumulate.

No token is ever recorded

Not even a wrong one — a wrong token is usually a real credential with a typo, or the right one for a different daemon. The monitor is not given the token to store.

Plain HTTP on the LAN

Nothing encrypts the LAN path. On a tailnet, WireGuard does. On open Wi-Fi, nothing does — which is the real argument for the Tailscale route above.

--host 0.0.0.0 means the whole network, not just your phone. On your own Wi-Fi that is fine. On café or hotel Wi-Fi you are putting a token-guarded shell in front of everyone on that network, over plain HTTP. The token will not be guessed; the traffic is still readable. Prefer the tailnet when you are not at home.

The QR scans but the page will not load.
Almost always the phone is on a different network from the laptop — guest Wi-Fi and the main SSID are separate networks on most routers. Check the address in the URL matches what silkcode inference host reports, or move to the tailnet.
Can I run more than one daemon on the laptop?
Yes — give each its own --host/--port and project. Session ids are unique across instances and every session records which instance created it.
Do I need Tailscale for this to work at all?
No. On one network, the LAN address is enough. Tailscale buys you two things: it keeps working when you leave, and it encrypts the traffic.
Is my code sent anywhere?
Only to whichever model you chose. Point Silk Code at a server on your own hardware and nothing leaves your machines at all.
